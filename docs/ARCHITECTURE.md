# Архитектура ImageVault (v0.2.0, Этапы 0–1)

## Статус и границы

Документ описывает текущую реализацию, а не целевую архитектуру. Текущая версия — одно приложение, один каталог и одна SQLite БД.

Слои: Web UI / REST → services/CatalogService → core/* → database/* (SQLite WAL). MCP упоминается как возможное будущее расширение, но текущего MCP-сервера и MCP-инструментов нет.

## Состав приложения

- app.py — композиция приложения, конфигурация, БД, сервисы, маршруты, middleware и жизненный цикл worker threads.
- services/catalog.py — сервисный слой каталога.
- core/scanner.py — обход зарегистрированного root и индексирование изображений.
- core/volume_manager.py — идентичность, refresh и rebind носителей.
- core/job_manager.py — SQLite-backed очередь фоновых задач.
- core/image_loader.py — метаданные и WebP thumbnails.
- core/paths.py — безопасное разрешение путей.
- core/auth.py — Bearer authentication и browser cookie sessions.
- database/db.py — соединения, WAL, миграции, транзакции и backup.
- database/repository.py — SQL-операции.

Подробная карта находится в docs/PROJECT_MAP.md; последовательности операций — в docs/DATA_FLOWS.md.

## Аутентификация

- LAN включается явно; политика запуска без токена определяется app.py.
- Токен хранится в data/config.json и выводится в консоль только предусмотренными командами.
- Браузер: форма входа → POST /api/auth/login → HttpOnly SameSite=Strict cookie; сессии хранятся в auth_sessions, TTL — 30 дней.
- API-клиенты: Authorization: Bearer <token>; сравнение выполняется через hmac.compare_digest.
- Неуспешная проверка токена имеет фиксированную задержку; сам токен не логируется.
- Проверки Origin и сетевые ограничения реализованы на уровне приложения и middleware; перед их изменением проверять app.py.
- Секреты не должны передаваться в URL.

## Миграции и БД

Миграции находятся в database/migrations/ и отслеживаются через PRAGMA user_version. Нумерация должна быть последовательной без пропусков. Каждая миграция выполняется транзакционно с BEGIN IMMEDIATE и COMMIT; при ошибке выполняется rollback.

Текущая последовательность: 0001_initial.sql и 0002_auth_sessions.sql (сессии и identity_warning).

Database создаёт одно соединение на поток, включает foreign_keys, busy_timeout и synchronous=NORMAL; при инициализации включает WAL. Database.tx() задаёт явную транзакцию. Не следует предполагать, что каждый метод repository автоматически открывает транзакцию.

## Идентичность носителей

Приоритет: marker UUID → Volume GUID → filesystem serial вместе с совпадающим label или fs_type, если соответствующие поля доступны.

Неоднозначное совпадение не разрешается автоматически. Повторяющийся marker на нескольких доступных mounts рассматривается как конфликт/предупреждение. Маркер записывается только по явному запросу; на системный диск требуется отдельное разрешение.

На Windows probing использует volume GUID и сведения файловой системы. На не-Windows системах текущая реализация использует st_dev и имя выбранного каталога; это не эквивалентно полноценной переносимой идентичности физического тома.

## Root и сканирование

- Сканирование выполняется в пределах зарегистрированного root.
- Инкрементальный fast path: существующая запись со статусом ok и совпадающими file_size + mtime_ns пропускает повторное чтение метаданных. Это не криптографическая проверка содержимого.
- Поддерживаемые расширения: PNG, JPG, JPEG, WebP.
- missing-фаза выполняется только если обход не зарегистрировал directory listing/stat/access errors.
- При таких ошибках результат содержит missing_check=skipped_incomplete_walk; иначе missing_check=complete.
- Исключённые, скрытые, недоступные и намеренно пропущенные пути защищаются от ложного missing.
- Переименование каталога в скрытый имеет специальное правило сохранения записей по прежнему имени.
- follow_symlinks=False по умолчанию. При включении ссылка может быть пройдена только если canonical target находится внутри зарегистрированного root, а не просто на том же томе.
- Для предотвращения повторного обхода/циклов используется visited set на основе (st_dev, st_ino).
- Отмена кооперативная: scanner проверяет её в начале итераций обхода и через progress(); отдельного checkpoint непосредственно перед missing-фазой нет. Поздний запрос отмены не гарантирует пропуск этой фазы.

На Windows path_key использует casefold; SQLite COLLATE NOCASE используется в SQL-сравнениях и не является полноценным Unicode case folding.

## Очередь задач

- Состояние задач хранится в SQLite.
- Worker атомарно забирает pending job через UPDATE ... RETURNING.
- checkpoint() проверяет запрос отмены и обновляет heartbeat; progress() записывает прогресс и затем проверяет отмену.
- Отмена кооперативная и зависит от конкретного handler.
- Пауза запрещает забирать новые задания, но не останавливает уже выполняемую задачу.
- При старте все записи со status=running переводятся в pending без проверки возраста heartbeat. Это не lease-based recovery.
- Код не должен считаться безопасным для нескольких одновременно работающих экземпляров приложения без отдельного анализа.

## Миниатюры

Метаданные и thumbnail создаются чтением оригинала. Thumbnail — производный WebP-файл в каталоге данных; ориентация EXIF применяется к превью. Для анимированного WebP используется первый кадр. Запись thumbnail выполняется во временный файл с последующим os.replace().

## Известные ограничения

- FAT/exFAT могут иметь грубую точность mtime.
- Реальную смену буквы диска следует проверять на физическом сменном носителе.
- POSIX volume identity — упрощённая реализация на основе st_dev.
- Thumbnail handler сейчас не использует cancellation checkpoints.
- Схема БД содержит таблицы для будущих возможностей; наличие таблиц не означает, что соответствующие workflows реализованы.
- Multi-catalog, per-catalog DB, global scheduler, video, duplicate search, AI analysis и MCP относятся к целевой архитектуре, описанной отдельно в docs/ARCHITECTURE_ADDENDUM.md.
